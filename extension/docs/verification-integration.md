# Verification Platform consumption

Installing or upgrading these overlays requires no Verification Platform installation. Existing workflow behavior remains available without it. The published `v0.1.0` release at `https://github.com/ahhakopian/verification-platform` is the current reference contract set; this reference does not install or select the platform for a project. Each consuming project still selects resources only through its own immutable `.verification/platform.json`. A project-level binding alone does not adopt an unrelated feature; justified non-applicability resolves no platform resources and adds no binding fingerprint. Specify/Clarify identify obligations without requiring runtime availability.

For a current feature with applicable approved obligations, this adapter consumes one project-selected immutable Verification Platform set through `.verification/platform.json`; it owns no universal schema/runtime. No release is bundled or implied by these instructions. Resolve exact indexed `contracts/verification-integration.md`, plan schema and descriptors. Missing/mixed/unsupported resources block only that applicable proof boundary. Never reconstruct schema or select latest.

Specify/Clarify identify irreducible browser/native proof from governing sources. Plan writes `## Verification Integration`, `Applicability: applicable` or `Applicability: not applicable`, with `Reason:` and source references. Derive `<FEATURE_DIR>/browser-verification-plan.json` explicitly from native feature context, regardless of AVAILABLE_DOCS. Applicable proof uses the platform validator with explicit installed/offline resolution, then semantic coverage/proof-fitness review. Non-applicable proof has justification and no placeholder JSON. Existing unadopted/completed features are not migrated automatically.

An adopted Plan has exactly one integration section and one applicability value.
Malformed, missing or contradictory classification requires Plan reconciliation;
it cannot silently become non-applicable. A pre-integration feature without a
section and without a proof JSON retains its existing behavior. A proof JSON
without its Plan disposition requires reconciliation.

Generic sufficiency adds no project hooks. Existing authoritative diagnostics need only a minimal binding adapter. Genuine missing internal sources need approved design/provenance/effects and tasks after existing proof-budget review. Generic platform gaps remain external dependencies. Material proof/product decisions return upstream; runtime availability is not assumed. Planned providers suffice for development readiness; real callable exports are required at execution.

Tasks reads the conditional JSON and orders approved support/configuration before dependent verification, retaining task IDs/marks. Existing Guard performs current structural validation through the platform CLI and semantic traceability/support/compatibility review; do not add another gate. Analyze includes the same conditional artifacts. Guard 5 → MVP Preflight 10 → Solo Readiness 15 → Core remains unchanged.

Plan/UX, Tasks/Guard and Readiness bind conditional JSON, neutral binding and referenced normative provider declarations. Fresh checks re-resolve external resources against local pins. Executable implementations, live settings and results stay outside development-readiness fingerprints. Solo uses explicit `VERIFICATION_PLATFORM_VALIDATOR` (installed JS CLI entry) and `VERIFICATION_PLATFORM_RESOURCES` (matching distribution/snapshot root) as resolution configuration; these are not release identity or approval inputs. CLI stdin supplies exact binding and plan bytes. Missing artifacts route to native Plan reconciliation before approval.

Stable fixture/provider configuration decisions that affect approved proof must
be declared in the existing feature `contracts/` or `design/` inputs, or in a
referenced normative declaration using the schema's `provider-declaration`
purpose. Such a design declaration must exist before approval even when its
implementation is planned. Tasked executable fixture/provider entries, live
runtime configuration and result files are not readiness inputs. Delivering
them satisfies later execution prerequisites without changing approved task
scope; changing the normative configuration declaration requires fresh review.

Existing verification tasks hand off exact feature-checked plan/digest, resolved binding, current authorization, actual fixture/config/provider versions and normal assignment to verification-orchestrator. The adapter checks native feature/ROADMAP and current approvals; platform does not read process state. Missing compiler/runtime/config is explicit BLOCKED. No new Solo stage, registry field or handoff manifest is added.

The maintained Solo `Repository.verification_handoff(assignment)` is the
transient existing-task adapter entry. It checks the current active native
feature and current Spec/Plan/Tasks/Readiness approvals, verifies current
plan/binding authorization and complete indexed resources, and returns the
ordinary platform invocation. Caller effects remain explicit; approval
references are provenance and create no permissions. The compiler subsequently
checks actual exports/types/source identities/readiness. Static planned
configuration labels remain approved design; execution requires delivered
referenced files rather than rewriting normative progress.

Completion reads complete current result/manifest/mandatory evidence, human proof and delivered support before lifecycle `--verification PASS`. FAIL/BLOCKED/INCONCLUSIVE, stale/missing proof or green runner without evidence cannot pass. Preserve evaluator flags/evidence and Human Acceptance authority. Publish stable project-relative evidence and explicitly include binding/evidence in acceptance inputs. No active feature is adopted merely by installing these maintained instructions.

The completion adapter requires the result, complete manifest, current claim
records, accepted evidence envelopes and their raw attachments as explicit
project-relative evidence/acceptance inputs, together with the neutral binding.
Transient files outside the project cannot satisfy this publication boundary.
The platform-owned current-result validator establishes mandatory coverage,
human proof, attachment integrity and current source/input identities; the
adapter never substitutes runner exit status or its own proof rules.
